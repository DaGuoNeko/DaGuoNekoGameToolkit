# 开发指南

[返回项目首页](../README.md) · [架构说明](架构说明.md) · [使用指南](使用指南.md) · [共享工作规则](../AGENTS.md)

文件路径默认相对仓库根目录；所有 npm、Node 测试及下方原生构建命令在 `DesktopUI/` 执行。以当前脚本和锁文件为准，不使用旧交接中的机器路径、PID 或通过数量作为当前状态。

## 环境要求

| 用途 | 要求 |
|---|---|
| 普通界面和主进程开发、出包 | Windows x64、Node.js 22.12+、npm、Windows PowerShell、.NET Framework C# 编译器 |
| 安装依赖 | `DesktopUI/package.json` 与 `package-lock.json`，使用 `npm.cmd ci` |
| 重编自有 C/C++/汇编桥及原生测试探针 | Zig 0.13.0；普通 JS 开发可使用仓库已有运行库 |
| 游戏实测 | 自行安装对应网易开发版游戏，使用专用测试地图和模组 |
| 官方 UI 引擎预览 | MCStudio 配套 `Minecraft.Windows.Editor.exe` 及资源 |
| 官方 Tracy 窗口 | 自行准备兼容的 `tracy-profiler.exe`，当前协议为 0.11.1 |
| 远程联机实测 | 固定版本 EasyTier 组件由应用首次使用时获取；房主另备樱花 TCP 隧道 |

网络助手使用 `%WINDIR%/Microsoft.NET/Framework64/v4.0.30319/csc.exe`。构建会检查已缓存网络组件的哈希；没有缓存时按 `native/network-helper/runtime-files.json` 生成助手和清单，不要求预先下载 EasyTier。

普通构建无需桌面 Python，也不需要 Python `.venv`。游戏内 Python 2.7 与独立的 Python MCP 工具是不同运行时。Node、Zig 可以另行使用便携目录，但仓库当前未提供自动下载或自动切换工具链的入口，不应把目录规划视为已实现功能。

|---|---|---|

| 可重复回归与固定夹具 | `DesktopUI/tests/`、`tests/fixtures/` | 提交，不包含个人存档或凭据 |

| 临时方案、调查笔记、草稿 | `.miao/notes/` | 被忽略；有长期价值的结论整理到 `docs/` |
| 专用临时样本、测试地图副本 | `.miao/test-data/` | 被忽略；真实地图先正常关闭并复制，不能把忽略当备份 |
| 本机自备便携工具或下载缓存 | `.miao/tools/`、`.miao/cache/` | 被忽略；脚本须显式使用，目录名不会自动配置环境 |
| npm 依赖 | `DesktopUI/node_modules/` | 被忽略；提交 package/lockfile，由 `npm ci` 重建 |
| 应用构建和分发文件 | `DesktopUI/dist/`、`DesktopUI/release/` | 被忽略；通过构建生成和单独分发 |
| UI 截图、测试报告等输出 | `DesktopUI/test-results/` | 被忽略；测试自身创建的系统临时目录由对应测试管理 |
| 原生编译中间件和探针 | `DesktopUI/native/<组件>/build/` | 被忽略；发行组件复制至约定 runtime 路径 |
| 必要运行二进制、更新脚本和许可证 | `DesktopUI/runtime/`、`licenses/` | 按现有清单提交；`runtime/update-config.json` 和 `runtime/automation/` 由构建生成，runtime 并非整个忽略 |
| 生成的网络助手、网络缓存、运行脚本副本 | `runtime/network/` 的指定文件、`runtime/automation/`、`native/network-helper/RuntimeHashes.cs` | 被明确规则忽略；来源和固定哈希仍提交 |

表中的临时子目录是使用约定，按任务需要创建，不必先生成空目录。正式测试不应长期藏在 `.miao/`；临时脚本成熟后再将所需部分纳入 `tests/` 或 `scripts/`，并补充验证。

`.gitignore` 对未跟踪文件起作用，已经被 Git 跟踪的文件不会因新规则自动退出版本控制。被忽略不代表已备份、已同步或可以公开；换设备时这些目录不会随 clone 恢复。源码仓库不保存机器交接资料，现有针对旧交接文件名的忽略规则用于防止误加入。

`.env`、`.env.*`、`.mcdev.json`、IDE 缓存、日志及备份扩展名也有忽略规则，但当前程序不会仅因出现 `.env` 就自动加载它。不要在源码、临时脚本、测试、文档或日志中写入真实密钥。新增文件后检查 `git status --short`，必要时用 `git check-ignore -v -- <路径>` 核对规则。

## 安装与构建

从仓库根目录进入应用目录：

```powershell
Set-Location DesktopUI
npm.cmd ci
npm.cmd run build
```

`npm ci` 按锁文件安装，并会重建已有 node_modules；只在首次准备或依赖变更等需要时执行。不要为解决环境问题随意升级所有依赖或借用另一个产品的 node_modules。

`build` 会编译网络助手与窗口观察/截图助手，使用 esbuild 生成界面、主进程、两个 worker 和 MCP stdio 构建，并复制 preload、HTML、图标及自动化脚本。`scripts/build-capture.ps1` 使用系统 .NET Framework 编译器及 Windows WinRT 元数据，将 `electron/automation-window.cs`、`electron/automation-capture.cs` 编译到被忽略的 `runtime/automation/automation-window.dll`；不需要额外下载 Windows SDK。其他原生 DLL/WASM 不会全部重编。应用实际入口为 `dist/main.cjs`。

构建保留 `mainFields: ["module", "main"]`，避免 jsonc-parser 选到 UMD 后留下缺失的相对 require。WASM 构建会去除调试路径元数据，保留执行节；运行库、worker 和普通 Node 的外置入口应按打包白名单核对。

## 开发启动与测试隔离

`npm.cmd start` 先构建再运行 Electron；当前没有配置工具箱源码的 watch/HMR。修改应用源码后重新构建、重开，不能把游戏模组热更新当成 Electron 源码热更新。

不设置环境覆盖时，源码应用使用日常 `%LocalAppData%/DaGuoNeko_GameToolkit/` 数据，并登记 MCP 启动入口。开发前明确是否允许使用该数据，避免无意将日常 MCP 指向开发构建。

| 变量 | 作用与限制 |
|---|---|
| `DGN_GAME_DATA_DIR` | 指向专用测试数据目录，改变配置、日志、MCP 和测试存档位置；同时影响部分外部进程冲突检查，不能作为真实游戏完全隔离的保证 |
| `DGN_GAME_HEADLESS=1` | 自动化隐藏窗口并跳过部分关闭确认，仅用于测试 |
| `DGN_GAME_TEST_EXE` | 支持该变量的 UI 测试使用指定的实际发行 EXE |
| `DGN_UI_BUNDLE_DIR` | multi-hosts/rooms 等夹具测试读取指定构建资源，先查对应测试的参数 |
| `DGN_TEST_RELOAD_SOURCES=1` | multi-hosts UI 测试开启来源变化与重启专项 |

优先使用现有 UI 测试创建的独立临时数据和测试启动器。手动 UI 调试可以选用专用目录，但不得导入真实存档并据此宣称已经隔离。独立主机仍使用其专用用户目录，官方编辑器引擎也有真实 Roaming 下的世界目录；环境变量不能替代路径和进程归属校验。

测试结束恢复修改前的环境变量值。真实游戏验证使用明确的测试存档、已核对的 EXE、自己的会话及源码来源，不覆盖日常游戏设置或结束未知进程。

## 测试与验收

先跑与改动直接相关的检查，再完成必要回归；以下命令不是每次必须全部执行的串行脚本。

| 层 | 入口 | 验证范围 |
|---|---|---|
| 服务逻辑 | `npm.cmd test`；或 `node --test tests/<目标>.test.cjs` | 配置、状态机、进程边界、日志、存档、协议和失败路径 |
| 串行服务回归 | `node --test --test-concurrency=1 tests/*.test.cjs` | 高负载时区分并发环境问题；记录失败及复测，不放宽产品保护 |
| 常规 UI | `npm.cmd run test:ui` | 当前 UI 测试集合使用测试启动器和临时数据 |
| 调试 UI | `npm.cmd run test:debug-ui` | 模拟游戏与真实鉴权通信下的调试流程 |
| 多主机与房间 UI | `node tests/multi-hosts-ui.cjs`、`node tests/rooms-ui.cjs` | 专项夹具；不使用 DGN_GAME_TEST_EXE 选择真实发行 EXE |
| 版本选择与本机加入 UI | `node tests/game-versions-ui.cjs`、`node tests/local-join-ui.cjs` | 实际 IPC 与界面下的版本能力、目标选择及失败状态夹具，不等于真实游戏入房 |
| MCDK 运行链 | `node tests/worlds-runtime.cjs` | 实际 MCDK、隔离数据和测试游戏 EXE，不是真实 Minecraft |
| 最终发行 EXE | `node tests/distribution-ui.cjs`、`node tests/rooms-package-ui.cjs` | 先设置 DGN_GAME_TEST_EXE；首次启动、持久化及发行入口 |
| 真实游戏 | 按任务使用独立测试地图和目标会话 | 真正加载、持久化恢复、多人、资源和热更新行为 |

本机多组真实验收可显式设置 `DGN_LIVE_GAME_EXE` 后运行 `node tests/local-multiplayer-live.cjs`；指定 `DGN_GAME_TEST_EXE` 时改用最终发行 EXE。脚本新建两张地图、同 UUID/模块名的两份不同源码和四份私有运行目录，验证 UI/MCP 分别入房、房主玩家名单、A 组脚本热更与停止 A 后 B 仍可用；只保存并关闭该测试实例创建的会话，不使用真实业务地图或远程隧道。输出保存在 `test-results/` 和忽略的测试目录中。

默认服务测试并发度为 4。`tests/worlds-ui.cjs` 是 profiles UI 的兼容入口。原生隔离探针未构建时，对应测试会跳过，不能把跳过计作原生验证通过。模拟游戏、ASAR UI、发行 EXE 和真实游戏应分别报告；历史通过数量不是当前验收结果。

AI 控制专项见 [AI 自动化接口](AI自动化.md)：`tests/automation-control.test.cjs` 含真实 Windows 隐藏断言夹具，`tests/automation-ui.cjs` 验证 UI/IPC 与 MCP 互通，`tests/automation-live.cjs` 要求显式 `DGN_LIVE_GAME_EXE`，新建两份独立测试地图检查定向截图、固定拍摄和停止后另一主机仍可用。开发用 `scripts/toolbox-call.cjs --jsonl` 可复用同一 MCP 连接；该脚本不随发行包分发。

部分 Python 脚本验收需要测试进程 PATH 中的 `python` 为 Python 3；游戏自身的 Python 2.7 不受影响。若出现 `types.SimpleNamespace` 缺失，先核对测试解释器并在当前测试进程指定 Python 3 环境，不修改系统默认解释器或产品逻辑。

真实本机多人测试先核对 toolbox_status/list_worlds/list_clients，再 launch_world 并等待 game_ready；客机用 launch_joined_client 指定 hostSessionId、不同玩家名和独立 requestId，同一次请求重试复用原 ID。只有 autoJoin.phase=joined 才算实际入房。后续代码/重载操作核对 sessionId/generation；日志按工具实际 schema 调用，桌面键鼠串行。

版本相关回归：`node --test tests/engine-profile.test.cjs tests/global-game.test.cjs tests/client-join.test.cjs tests/local-client-isolation.test.cjs`，界面回归用 `node tests/game-versions-ui.cjs` 和 `node tests/local-join-ui.cjs`。前者覆盖程序指纹、启动竞态和构建拒绝；UI 覆盖能力表、未验证程序筛选、手动选择保存、房主版本锁定及停止后的失败提示。夹具不能替代实机证据。

真实单机双开脚本为 `node tests/local-multiplayer-live.cjs`，运行前把 `DGN_MULTIPLAYER_GAME_EXE` 指向待测游戏 EXE。它使用新建测试存档，经 MCP 启动房主/来宾，检查 `joined`、服务端玩家回执、指纹相同、目录隔离及定向停止；另外在房主运行后修改测试实例的全局程序，验证来宾仍跟随房主快照。只允许登记了完整隔离能力的构建；输出 `test-results/local-multiplayer-live.json`。缺少某构建时保留待验证状态，不以另一构建通过代替。

新增支持版本时，先核对 `electron/supported-engines.json` 的实际 SHA-256，再逐项验证原生桥、OreUI 菜单、玩家名、UDP 发现、入房回执和目录隔离。仅将通过的能力标为 true；自动入房与完整隔离是不同能力。网络助手由 build 从同一表生成名单，不能只改下拉框、目录名或静态说明。

## 出包与分发

```powershell
npm.cmd run package
```

此命令先构建，再生成 `release/DaGuoNeko-Game-Toolkit-win32-x64/`、带 package.json 版本号的 ZIP 和 `.sha256`。默认输出目录仍有工具箱运行时，改在 `release/build-时间戳/` 生成，保留正在使用的版本；以脚本输出为准。

包中包含 app.asar、指定 runtime、licenses、`distribution/使用说明.txt`、`release-info.json` 和逐文件 `SHA256SUMS.txt`。EasyTier 等首次下载的网络组件不进入分发 ZIP。源码、研究资料、测试输出和个人数据不随包分发。

### 私有 GitHub Release 更新

版本更新使用当前私有仓库的 GitHub Release。每个版本必须上传以下两个资产，名称必须与 `package.mjs` 生成的版本一致：

```text
DaGuoNeko-Game-Toolkit-<version>-win-x64.zip
DaGuoNeko-Game-Toolkit-<version>-win-x64.zip.sha256
```

客户端不会内置维护者 Token。仓库的 `electron/domains/update/update-config.cjs` 保存公开的 OAuth App Client ID、仓库地址和 scope，普通 clone/build 无需创建新应用或复制本机忽略文件。构建每次从这个共享配置生成 runtime 配置；不再沿用上次构建留下的隐藏设置。只有维护者更换应用时才使用 `DGN_UPDATE_GITHUB_CLIENT_ID` / `DGN_UPDATE_GITHUB_SCOPE` 覆盖。Client ID 是公开标识，不是密钥；不能提交 Client Secret、PAT 或用户令牌。

日常迭代发布（拥有仓库写权限的成员）：

```powershell
npm.cmd version patch --no-git-tag-version
# 编写 ../docs/releases/<新版本>.md，更新 README 中的版本，完成本地测试后提交。
git add package.json package-lock.json ../README.md ../docs/releases
git commit -m "feat: 发布工具箱新版本"
git tag v<新版本>
git push origin main
git push origin v<新版本>
```

`.github/workflows/release.yml` 在版本标签推送时运行 Windows 构建、服务测试、更新 UI 和发行 EXE 检查，再生成完整 ZIP。工作流使用 GitHub 自动提供的 `GITHUB_TOKEN`，只在发布任务授予 `contents: write`，无需成员每次申请 PAT 或用浏览器上传文件。仓库需允许 Actions 运行；该权限属于仓库初始化设置，日常发布不需要更改。工作流失败不会发布半成品；可从 Actions 的 Run workflow 输入同一标签重试。已发布的正式版本禁止覆盖，后续修复递增版本号。

本地紧急发布仍可使用 `npm.cmd run package`、`npm.cmd run release:publish -- <产物所在目录>`，需要从 GitHub 官方安装 `gh` 并完成一次 `gh auth login`，之后复用已保存的登录。发布脚本检查干净工作区、标签提交、ZIP 中的版本与构建提交、SHA-256 和版本说明；仅上传到草稿，两个资产都成功后才正式发布。不从浏览器读取 Cookie，不要求用户每个版本重新授权，也不要把 Token 放进命令参数或项目文件。

若 Windows 上浏览器可访问 GitHub，而 Git 连接持续失败，先核对网络和当前 Git 支持的 TLS 后端。只有支持 OpenSSL 的 Git 构建才可尝试 `git config --local http.sslBackend openssl`；出现 Unsupported SSL backend 时用 `git config --local --unset http.sslBackend` 恢复默认。这是单仓库设置，不修改其他仓库，也不关闭证书校验；网络代理或组织权限问题仍需按实际错误处理，不能用 `sslVerify=false` 绕过。

`docs/releases/<version>.md` 是该版本发布说明来源，工作流将它写入 GitHub Release body。客户端读取最新正式 Release 和分页历史列表（每页 30 条），不显示草稿；历史中的预发布标记展示，但不作为自动安装目标。缺少 ZIP 或校验文件的 Release 仍可展示说明，下载按钮不可用。GitHub `/releases` 返回空数组表示仓库可读但没有发布；404 表示路径或权限问题，不能一概解释为“没有版本”。请求使用 Electron 网络栈沿用系统代理。

另一名成员在新设备 `git clone` 后运行 `npm.cmd ci`、`npm.cmd start`，共享 Client ID 已生效，只需首次用自己的 GitHub 账号授权。必须有该私有仓库读取权限并接受邀请；组织可能另需 OAuth/SSO 批准。授权由当前 Windows 用户的 safeStorage 保存，重开及升级复用；主动撤销、失效或换 Windows 用户时需重新授权。当前 OAuth App 的 `repo` scope 是 GitHub 提供的较宽权限，无法假装为单仓库只读；若以后改为公开二进制分发或 GitHub App，需要单独确认访问模型。

安装前先停止本工具游戏、房间并保存草稿。独立 PowerShell 脚本从缓存目录运行，重新校验 ZIP 的 SHA-256、路径、版本和 EXE/ASAR 结构；在程序同一磁盘暂存，等待旧进程退出后切换目录。每次保留唯一的 `.previous-<随机值>` 备份，不删除已有备份；切换或操作系统启动调用失败时尝试恢复，不把启动后业务崩溃宣称为自动回滚。结果保存在用户数据的 `update/update-result.json`，失败原因会在下次启动的更新页展示；旧备份需用户在确认新版本正常后自行清理。用户数据目录不参与替换。

更新专项验收：`node --test tests/update.test.cjs tests/update-install.test.cjs tests/update-launcher.test.cjs` 验证网络状态、历史分页、凭据隔离、完整性、实际 Windows 文件替换及更新进程在客户端退出后继续执行；`node tests/update-network.cjs` 用实际 Electron 网络栈验证手动重定向、流式响应与取消；`node tests/update-ui.cjs` 使用真实构建界面、preload、IPC 和服务，仅模拟 GitHub 网络边界，保存启动/定时弹窗及浅/深色历史界面截图。网络夹具不等于真实 GitHub 发布验收。

已有本机成员授权时，指定 `DGN_GAME_TEST_EXE` 后显式运行 `node tests/update-live-ui.cjs`，验证真实发布和界面。该测试只复制工具箱自身的加密授权文件及对应 Electron Local State 到临时隔离目录，不复制浏览器登录信息、不输出明文令牌，结束后清理测试目录；缺少授权时应先在正常工具箱中完成首次授权。另需验证真实更新包下载及升级结果，不能只以版本接口成功代替完整安装验收。

GitHub Windows runner 的默认 TEMP 可能含 `RUNNER~1` 短路径。工作流使用 `fs.realpathSync(RUNNER_TEMP)` 设置本次任务 TEMP/TMP，避免短路径触发项目的目录重定向保护；不通过放宽产品路径校验来让测试通过。

Windows 安装进程由 `native/update-launcher/Program.cs` 编译的无窗口启动器托管。构建自动生成 `runtime/native/update-launcher.exe`，无额外管理员授权。启动器和脚本复制到更新缓存后运行，主程序收到含进程身份和版本的准备回执才退出；否则保留窗口和专属日志。不能直接把 PowerShell 标记 detached，也不能让安装程序随客户端退出。准备完成后再次检查游戏/房间/草稿，条件变化会写取消标记，在替换前终止。

完整升级验收应以正常进程方式启动隔离的低版本客户端，再连接其界面；核对安装目录版本、自动重启、窗口可见、授权和用户数据保留。部分测试启动器会在目标退出时收回子进程，不能把这种运行方式当成安装重启成功的证明。只对后台启动器隐藏窗口，重新启动的客户端使用正常窗口样式。0.1.0–0.1.2 用户需先解压运行 0.1.4 完整包一次；0.1.3 升级后窗口未显示时可重新打开软件恢复。

出包后对本次实际 EXE 验证，而不是默认测试旧目录。支持的测试变量可按下例临时设置（路径替换为本次产物）：

```powershell
$previousTestExe = $env:DGN_GAME_TEST_EXE
try {
    $env:DGN_GAME_TEST_EXE = (Resolve-Path 'release/DaGuoNeko-Game-Toolkit-win32-x64/DaGuoNeko-Game-Toolkit.exe').Path
    node tests/distribution-ui.cjs
    if ($LASTEXITCODE -ne 0) { throw '发行入口验证失败' }
    node tests/rooms-package-ui.cjs
    if ($LASTEXITCODE -ne 0) { throw '发行房间界面验证失败' }
} finally {
    if ($null -eq $previousTestExe) {
        Remove-Item Env:DGN_GAME_TEST_EXE -ErrorAction SilentlyContinue
    } else {
        $env:DGN_GAME_TEST_EXE = $previousTestExe
    }
}
```

Electron 缓存缺失时允许打包器正常下载；网络失败不等于源码错误。ASAR、dist、外置运行文件、许可证与 ZIP 应对应同一次构建。普通 Node/helper 的脚本不能依赖 Electron 的 ASAR 读取能力。

不要覆盖正在运行的发行目录。分发完整 ZIP，不单独分发 EXE。软件与源码目录不同，构建不会自动更新其他桌面副本；新版启动还可能更新本机 MCP 登记，切换前先保存自己的游戏进度。
